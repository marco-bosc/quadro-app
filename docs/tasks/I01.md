# Incarico I01 — Base funzionante

## Obiettivo

Due aziende fittizie isolate. Un utente accede, crea una bozza minima, la salva e la riapre.
L'utente di un'azienda non vede né modifica i dati dell'altra.

## Fuori perimetro

Niente AI, PDF, invii, lead, clienti, righe economiche, calcoli, Cloud Functions, Storage, deploy.
Niente grafica rifinita: interfaccia pulita e usabile da smartphone, senza librerie UI.

## Da realizzare

1. **Progetto:** Vite + React + TypeScript; SDK Firebase; Vitest; ESLint; `.gitignore`; `.env.example`; `README.md`
   con istruzioni di avvio nel codespace.
2. **Firebase:** `firebase.json` con emulatori Auth, Firestore e Hosting (UI degli emulatori attiva);
   `firestore.rules` e `firestore.indexes.json`. Collegati al progetto alias `test` di `.firebaserc`.
   L'app usa gli emulatori in sviluppo e non tocca mai i servizi reali.
3. **Modello dati minimo:**
   - `memberships/{uid}` → `{ companyId, role: "owner", createdAt }`. Scrivibile solo da script di amministrazione, mai dal client.
   - `companies/{companyId}` → `{ name, createdAt }`.
   - `companies/{companyId}/quotes/{quoteId}` → `{ title, notes, status: "draft", version, createdBy, createdAt, updatedAt }`.
4. **Security Rules:** lettura e scrittura su `companies/{companyId}/**` solo se `memberships/{request.auth.uid}.companyId == companyId`.
   Un utente legge solo la propria membership. Validazione dei campi della bozza (tipi, lunghezze massime, `status` solo `"draft"`).
5. **Script `npm run seed`:** crea negli emulatori due aziende (es. "Elettrica Rossi" e "Impianti Bianchi"),
   un utente per ciascuna con email e password fittizie, le membership e una bozza di esempio per azienda.
6. **Interfaccia:**
   - Accesso con email e password, uscita.
   - Elenco bozze dell'azienda, dalla più recente.
   - Nuova bozza e modifica: titolo e note.
   - Pulsante **Salva** esplicito; avviso visibile di modifiche non salvate; avviso del browser se si lascia la pagina con modifiche non salvate.
   - Il salvataggio usa il campo `version` in una transazione: se il documento è cambiato nel frattempo, il salvataggio fallisce
     con un messaggio chiaro e le modifiche dell'utente restano a schermo.
   - Errori di rete o di permessi mostrati in italiano, mai un salvataggio dichiarato riuscito se non lo è.
7. **Script npm:** `dev` (emulatori + Vite), `check` (lint, typecheck, build, test), `seed`, `test:rules`.

## Criteri di accettazione

- [ ] Dopo `npm install`, `npm run dev` e `npm run seed`, l'app si apre nel codespace e l'accesso funziona con gli utenti fittizi.
- [ ] L'utente di Elettrica Rossi crea una bozza, la salva, ricarica la pagina e la ritrova invariata.
- [ ] L'utente di Impianti Bianchi non vede le bozze di Elettrica Rossi.
- [ ] Test delle regole (sugli emulatori) che dimostrano che l'utente A **non** può: leggere una bozza di B conoscendone l'ID,
      elencare le bozze di B, scrivere in B, creare o modificare una membership, leggere la membership di B.
- [ ] Test che un utente non autenticato non legge né scrive nulla.
- [ ] Test del conflitto di versione: due salvataggi concorrenti sulla stessa bozza, il secondo fallisce senza sovrascrivere.
- [ ] `npm run check` passa senza errori.
- [ ] Nessuna credenziale o file `.env.local` nel repository.

## Prima di iniziare

- Chiedimi se il codespace è aperto da VS Code desktop o dal browser, e scegli di conseguenza
  come far raggiungere gli emulatori all'app. Documenta la scelta nel README.
- Riassumi il piano in poche righe e aspetta la mia conferma.
